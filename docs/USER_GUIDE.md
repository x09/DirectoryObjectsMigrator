## Введение

Directory Objects Migrator — инструмент для миграции объектов Active Directory из Microsoft AD в Samba AD.

### Возможности

- ✅ Миграция подразделений (OU)
- ✅ Миграция пользователей
- ✅ Миграция групп с членством
- ✅ Миграция контактов
- ✅ Сохранение иерархии подразделений
- ✅ Трансформация атрибутов (UPN, email)
- ✅ Отложенное членство в группах (DEFERRED)
- ✅ Идемпотентные повторные запуски
- ✅ Режим симуляции (Dry Run)
- ✅ Детальное логирование
- ✅ Генерация отчетов (HTML/TXT)

### Ограничения

- ❌ Пароли пользователей НЕ мигрируются (устанавливаются случайные)
- ❌ DNS зоны не мигрируются
- ❌ GPO не мигрируются
- ❌ Компьютеры не мигрируются

## Установка

### Системные требования

- ALT Linux (или совместимая система)
- Python 3.10+
- Права root для установки

### Установка зависимостей

```bash
# Запустите установочный скрипт
sudo ./install.sh
```

Или вручную:

```bash
# Установка пакетов
sudo apt-get install python3-module-ldap3 python3-module-PyQt5 \
                     python3-modules-sqlite3 python3-module-yaml

# Компиляция переводов
python3 compile_translations.py
```

## Настройка подключений

### Открытие настроек

**File → Settings** или нажмите **Analyze** (откроется автоматически, если не настроено)

### Вкладка Source DC

Настройки исходного контроллера домена (Microsoft AD):

- **Host / IP Address**: IP или hostname контроллера домена
- **Port**: 389 (LDAP) или 636 (LDAPS)
- **Domain**: Имя домена (например: `source.alt`)
- **Username**: Имя администратора (например: `administrator`)
- **Password**: Пароль администратора
- **Use TLS**: Шифрование соединения (рекомендуется)

**Кнопка "Test Connection"** — проверка подключения.

### Вкладка Destination DC

Аналогично для целевого контроллера (Samba AD).

### Вкладка Migration Options

**Performance:**
- **Batch Size**: Количество объектов, обрабатываемых за раз (по умолчанию 100)

**Password Policy:**
- **Random Password**: Случайные пароли для пользователей
  - **Length**: Длина пароля (по умолчанию 12)
- **Fixed Password**: Один и тот же пароль для всех пользователей
  - Введите пароль в поле ниже

**Важно**: Все пользователи создаются в отключенном состоянии (disabled). Администратор должен:
1. Установить финальные пароли
2. Включить учетные записи

### Сохранение настроек

Нажмите **Save**. Адреса, порты, домены и имена пользователей сохраняются в
конфигурационный файл, **пароли — нет** (из соображений безопасности).

Пароли запрашиваются один раз за сеанс работы программы и хранятся только в
памяти. Повторные нажатия **Analyze** и **Start Migration** пароль не спрашивают.
Если пароль оказался неверным, он сбрасывается, и при следующей попытке
подключения программа запросит его снова.

## Выполнение миграции

### Шаг 1: Указать Base DN

В поле **Base DN for Migration** введите DN контейнера или OU, который нужно мигрировать:

```
OU=Users,OU=Company,DC=source,DC=alt
```

Все объекты внутри этого DN (включая вложенные OU) будут мигрированы.

Начиная с v1.1, вместо ручного ввода можно нажать **«Выбрать…»** рядом с
полем Base DN. Откроется дерево исходного домена:

1. Если потребуется, введите пароль исходного DC. Подключение к целевому DC
   для просмотра дерева не требуется.
2. Раскрывайте ветки, чтобы увидеть вложенные подразделения (OU) и контейнеры.
   Дочерние ветки загружаются при раскрытии, в фоновом режиме. Пока идёт запрос,
   рядом с названием ветки показано «Загрузка ветки…», а под деревом —
   анимированный индикатор без процентов. После завершения загрузки или ошибки
   отметка исчезает; индикатор скрывается, когда завершены все запросы.
3. Выделите **одну** ветку. Полный DN появится под деревом.
4. Нажмите **«Выбрать»**. DN будет подставлен в главное окно. Для запуска
   миграции выполните анализ выбранной области.

Можно выбрать OU, контейнер или корень домена. В область входят все вложенные
объекты, но правила исключения и фильтрация служебных объектов продолжают
действовать. Дерево показывает только структуру, видимую вашей учётной записи.
Просмотр дерева не создаёт и не изменяет объекты каталога.

Кнопка **«Обновить дерево»** перечитывает структуру с корня. Если загрузка ветки
завершилась ошибкой, раскройте её повторно. Пока идут запросы, обновление
недоступно. Закрытие диалога во время запроса дождётся его завершения или сетевого
тайм-аута; интерфейс при этом остаётся отзывчивым.

Ручной ввод DN сохранён. Любое изменение Base DN сбрасывает предыдущий план:
перед миграцией нужно снова нажать **«Анализ»**. Отмена выбора сохраняет прежний DN.


### Шаг 2: Режим Dry Run (опционально)

Если хотите **протестировать** миграцию без фактического создания объектов:

✅ Установите чекбокс **Dry Run Mode**

В этом режиме:
- Выполняется анализ
- Показывается что будет создано
- Логи пишутся
- Но **объекты НЕ создаются** в destination

### Шаг 3: Анализ

Нажмите **Analyze**.

Приложение:
1. Подключится к **обоим** контроллерам домена (пароль запрашивается один раз за сеанс)
2. Просканирует указанный Base DN в исходном домене
3. Классифицирует объекты (OU, Users, Groups, Contacts)
4. Сверится с целевым доменом и базой миграции
5. Покажет окно **Preview**

Целевой домен опрашивается именно на этом шаге — иначе предпросмотр не смог бы
отличить новые объекты от уже существующих.

### Окно Preview

Три вкладки:

**Planned actions** — что произойдёт с каждым объектом:

| Метка | Значение |
|---|---|
| 🟢 **CREATE** | объект будет создан |
| ⬜ **EXISTS** | уже перенесён ранее, будет пропущен |
| 🔴 **CONFLICT** | есть в целевом домене, но отсутствует в базе миграции — **перезаписан не будет** |
| 🔴 **ERROR** | не удалось проверить идентичность объекта или прочитать его данные |

Для каждой строки показаны исходный и целевой DN; в колонке причины поясняются ошибки проверки.

**Deferred references** — ссылки на объекты за пределами области миграции:

- 🟢 *Будет добавлено сейчас* — целевой объект уже перенесён, ссылка применится
- 🟠 *Целевой объект ещё не перенесён* — потребуется повторный запуск

**Objects found** — количество объектов по типам, включая игнорируемые.

Внизу — блок **Notes** с предупреждениями о конфликтах и напоминанием, что
учётные записи создаются отключёнными. Если создавать нечего, здесь указывается
конкретная причина: объекты отфильтрованы, по указанному DN ничего нет, всё уже
перенесено ранее или всё в состоянии конфликта.

### Проверка целевого пути и конфликтов (v1.2)

Предпросмотр проверяет наличие целевого родителя. Новая OU, запланированная раньше
потомка, считается доступным родителем; если её создание при выполнении завершится
ошибкой, потомок не будет создан. Родители вне выбранной ветки должны уже существовать.
Контейнеры не создаются автоматически. В качестве родителя поддерживаются OU,
контейнер и корень домена; объект другого класса по ожидаемому DN блокирует создание.

Кроме занятого DN, проверяются совпадения логина `sAMAccountName` и UPN после замены
суффикса во всём целевом домене, а также повторяющиеся идентификаторы среди новых
объектов плана. Причина появляется в колонке **Reason**. Проверки выполняются снова
перед созданием; при ошибке чтения объект не считается свободным для создания.

Основной анализ и итоговая проверка получают все LDAP-страницы по 500 записей.
Ошибка любой страницы прерывает чтение, не выдавая неполный список за полный.
Это не устраняет ограничения чтения отдельных многозначных атрибутов больших групп.

Проверки не гарантируют права записи и принятие всех атрибутов схемой сервера.
Изменение каталога между проверкой и LDAP-записью всё ещё возможно; ошибка записи
отражается в журнале и результате запуска. Проверка UPN ограничена целевым доменом,
а не всеми доменами леса.

### Парольная политика и отказ установки (v1.2)

В параметрах миграции показана исходная политика Samba AD: сложность включена,
минимальная длина 7, история 24, минимальный срок 1 день, максимальный 42 дня,
хранение открытых паролей выключено; порог блокировки 0 (отключена), время
блокировки и сброса счётчика — 30 минут. Это значения по умолчанию для справки,
а не команда изменить домен. Фактическая политика сервера имеет приоритет.

Длина случайного пароля из окна настроек используется при генерации; по умолчанию
это 12 символов. Генератор учитывает доступный для чтения `minPwdLength` целевого
домена, включает четыре категории ASCII-символов и избегает логина и частей имени.
Принятие пароля при дополнительных ограничениях всё равно определяет сервер.

Если заданный или случайный пароль отклонён либо установка не подтверждена,
приложение журналирует событие и выполняет не более трёх дополнительных попыток
с новыми случайными паролями через `unicodePwd`. Переход к `userPassword` после
отказа больше не применяется. Успешная замена заданного пароля случайным отражается
как предупреждение, поскольку введённый оператором пароль уже не действует.

В разделе **Password setup** HTML/TXT-отчёта сохраняются исходы установки по
учётным записям. Пароли и их кодированные значения не включаются в журнал и отчёты.
Если все попытки неудачны, результат содержит ошибку; созданный объект сохраняется
в истории с отметкой о незавершённой установке. Повторный реальный запуск пытается
установить пароль только для такой отмеченной записи после проверки GUID. Dry Run
этого не делает. Успешно обработанные учётные записи не получают новых паролей
при каждом повторном переносе.

Пользователи остаются отключёнными. Перед включением администратор должен установить
известный пользователю пароль, если применялась случайная генерация. Подтверждение
LDAP-операции означает принятие сервером установки, но не заменяет отдельную проверку
входа пользователя.

### Содержательная проверка и отчёт (v1.2)

Проверяется каждый поддерживаемый объект выбранной ветки, а также родители
отложенных ссылок, созданных или разрешённых текущим запуском. Для объекта требуется
соответствие GUID в истории текущей пары доменов. Объект с тем же DN или логином
не заменяет эту проверку. Перемещённый целевой объект ищется по GUID, даже если
он больше не находится в исходно рассчитанной ветке назначения.

Ожидаемые значения готовятся теми же обработчиками и конфигурацией, что используются
при создании: учитываются преобразования UPN/email, исключения и вычисляемые поля.
Проверяются флаг отключённой учётной записи и заданный `primaryGroupID`; пароли
не сравниваются и не включаются в подробности. `accountExpires` переносится точным числом LDAP: значения 0 и
9223372036854775807 означают отсутствие срока действия и считаются эквивалентными.
Обычная дата в далёком будущем не считается значением «никогда».
Порядок многозначных атрибутов
неважен; одиночное значение и список из одного значения считаются эквивалентными.

Для `member`, `manager`, `managedBy` сравниваются целевые DN, полученные через
проверенные соответствия GUID. Проверяется прямой состав групп, включая вложенные
группы; эффективные права и транзитивное членство не рассчитываются. Отсутствующие
ожидаемые ссылки и лишние ссылки — ошибки. Неразрешённая ссылка с записью DEFERRED
остаётся предупреждением. Большие группы читаются полностью: ответы
`member;range=...` автоматически дополняются запросами следующих диапазонов.
Проверяются непрерывность диапазонов, количество значений и неизменность
`objectGUID`/`uSNChanged` между ответами. Ошибка или изменение объекта прерывают
чтение; повторите анализ после устранения причины. Частичный состав группы
не используется как полный. Это не заменяет атомарный снимок каталога.

Раздел **Verification details** в HTML/TXT-отчёте содержит DN объектов, атрибуты,
ожидаемые/фактические значения и причины ошибок чтения. Данные сохраняются в SQLite,
поэтому подробный отчёт можно повторно сформировать после перезапуска приложения.
Отчёт может содержать переносимые персональные данные пользователей.

Проверка выполняет только чтение каталогов и не меняет соответствия в базе.
Расхождения не исправляются автоматически. Сравниваются текущие данные, без
атомарного снимка обоих доменов: изменение атрибутов или членства во время работы
может проявиться как расхождение. Dry Run не проверяет результат отсутствующих
записей. Успешный результат не подтверждает пароли, ACL, эффективные права или
объекты и атрибуты, исключённые из области миграции.

### История миграции и проверка соответствий (v1.2)

История и отложенные ссылки разделены по паре исходного и целевого доменов.
Пара определяется по GUID корневых объектов доменов: другой контроллер того же
домена сохраняет историю, а заново созданный домен с тем же DNS-именем — нет.

Перед повторным использованием соответствия приложение проверяет GUID целевого
объекта. Переименование или перемещение внутри домена поддерживается: новый DN
находится по GUID. Если объект удалён, заменён другим с тем же DN или его
идентичность нельзя проверить, действие блокируется и показывается ошибка.
Приложение не пересоздаёт такой объект автоматически. Перед отложенным обновлением
проверяется также родитель ссылки, например группа, в которую добавляется участник.

Совпадения логинов `sAMAccountName` недостаточно для членства в группе или другой
ссылки. Нужна запись соответствия для текущей пары доменов с подтверждённым GUID.
Без неё ссылка остаётся DEFERRED. Это касается и объектов, созданных сторонними
средствами, и ранее перенесённых объектов после сброса SQLite-базы.

При обновлении старой базы автоматически создаётся резервная копия рядом с ней.
Старые записи относятся к паре доменов только при согласованной сохранённой истории;
их целевые GUID всё равно проверяются перед использованием. Неоднозначные записи
сохраняются без автоматического применения, с предупреждением в предпросмотре.
Для восстановления потерянных соответствий нужна подходящая резервная копия базы;
интерфейс ручного сопоставления пока отсутствует. Сброс базы очищает историю всех
направлений, а не только текущей пары доменов.

### Встроенные контейнеры (CN=Users, CN=Builtin и подобные)

По умолчанию встроенные контейнеры пропускаются, чтобы при сканировании всего
домена не переносить служебные объекты. Но если такой контейнер указан **явно** в
поле Base DN, правило для него отключается — считается, что это осознанный выбор.

| Base DN | Результат |
|---|---|
| `DC=win,DC=test` | содержимое `CN=Users` пропускается |
| `CN=Users,DC=win,DC=test` | содержимое `CN=Users` переносится |
| `OU=Sales,CN=Users,DC=win,DC=test` | переносится |

Остальные правила продолжают действовать в любом случае: учётные записи
компьютеров и другие неподдерживаемые типы пропускаются всегда, а `CN=Builtin`
останется отфильтрованным, если вы указали `CN=Users`.

Когда правило отключается, в журнал пишется предупреждение с указанием, какое
именно.

**Кнопки:**
- **Start Migration** (или **Start Dry Run** в режиме симуляции)
- **Cancel** — вернуться без изменений

### Шаг 4: Миграция

После нажатия **Start Migration** откроется окно **Progress**:

- Прогресс-бар (0-100%)
- Текущая фаза (1/5, 2/5...)
- Логи в реальном времени
- Кнопка **Cancel** для остановки

Повторный запрос пароля не производится — он уже сохранён в памяти на время сеанса.

**Фазы миграции:**

1. **Phase 0: Analysis** (0-20%) — Повторный анализ
2. **Phase 1: Creating OUs** (20-40%) — Создание подразделений (от корня к листьям)
3. **Phase 2: Creating objects** (40-60%) — Создание пользователей, групп, контактов
   вместе со всеми атрибутами
4. **Phase 3: Copying attributes** (60-80%) — Ничего не делает: атрибуты уже
   записаны на фазе 2 одной операцией. Фаза оставлена в конвейере как отдельный
   шаг на случай атрибутов, которые Samba принимает только вторым запросом.
5. **Phase 4: Resolving references** (80-95%) — Разрешение ссылок (member, manager),
   включая отложенные с прошлых запусков
6. **Phase 5: Verification** (95-100%) — Проверка соответствий GUID, значений
   переносимых атрибутов и состава ссылок, включая членство в группах.

### Шаг 5: Завершение

По завершении:

- **Завершена успешно** — выполнение и проверка завершились без выявленных проблем.
- **Завершена с предупреждениями** — остались отложенные ссылки, конфликты или
  предупреждения проверки; изучите журнал и отчёт.
- **Завершена с ошибками** — не все операции выполнены либо проверка выявила ошибки.
- **Отменена** — запуск остановлен пользователем.
- **Ошибка миграции** — выполнение прервано исключением; отчёт доступен, если
  запись запуска уже была создана.

Начиная с v1.2, неудачная запись ссылки не закрывает её в базе миграции.
При повторном запуске приложение повторяет попытку. Если запись в AD прошла,
но ответ был потерян, уже существующее значение распознаётся без повторной записи.

**Кнопка Close** — закрыть окно прогресса.

## Повторные запуски

### Идемпотентность

Приложение **безопасно** запускать повторно с тем же Base DN:

- ✅ Существующие объекты **не перезаписываются**
- ✅ Новые объекты **создаются**
- ✅ Отложенные ссылки **разрешаются**, если целевые объекты теперь существуют

### Сценарий: Поэтапная миграция

**Первый запуск:**
```
Base DN: OU=Department1,DC=source,DC=alt
```
Мигрирует пользователей и группы из Department1.

Группа `Group1` имеет члена `User5` из `OU=Department2` — эта ссылка будет **DEFERRED** (отложена).

**Второй запуск:**
```
Base DN: OU=Department2,DC=source,DC=alt
```
Мигрирует Department2, включая `User5`.

**Третий запуск:**
```
Base DN: OU=Department1,DC=source,DC=alt
```
Повторный запуск первого DN:
- Существующие объекты пропускаются (EXISTS)
- `Group1` обновляется: `User5` теперь добавляется в группу (был DEFERRED, теперь RESOLVED)

### Просмотр статуса

В логах вы увидите:

```
[SUCCESS] Created user: CN=User1,OU=Department1,DC=dest,DC=alt
[WARNING] CN=User2,OU=Department1,DC=dest,DC=alt - EXISTS
[WARNING] Deferred 1 member references for CN=Group1,...
```

## Устранение неполадок

### Приложение не запускается

**Симптом**: `ModuleNotFoundError: No module named 'PyQt5'` (или `ldap3`, `yaml`)

**Пояснение**: в ALT Linux системные пакеты Python лежат в
`/usr/lib64/python3/site-packages`, которого нет в стандартном `sys.path`.
`main.py` добавляет этот путь сам, поэтому запускать следует через `./run.sh`
или `python3 main.py`, а не импортировать модули проекта вручную.

**Решения:**

1. Проверьте зависимости: `./check_dependencies.sh` — скрипт использует тот же
   путь поиска, что и приложение, поэтому его результат совпадает с реальностью
2. Установите отсутствующие пакеты: `sudo ./install.sh`

**Симптом**: `setEnabled(): argument 1 has unexpected type 'str'`

Ошибка исправлена. Если она появилась снова — значит используется старая копия
файлов; обновите каталог проекта целиком.

### Интерфейс частично на английском

**Симптом**: главное окно переведено, а диалоги — нет

**Пояснение**: ошибка исправлена (язык сбрасывался при создании главного окна).
Если проблема осталась, скорее всего не собраны файлы переводов:

```bash
python3 update_translations.py    # обновить каталоги из исходного кода
python3 compile_translations.py   # собрать .mo
```

Проверить полноту перевода: `python3 update_translations.py --check`

### Ошибка подключения к DC

**Симптом**: "Connection failed" при Test Connection

**Решения:**

1. Проверьте IP/hostname контроллера домена
2. Проверьте порт (389 для LDAP, 636 для LDAPS)
3. Проверьте сетевую доступность (`ping <DC_IP>`)
4. Проверьте credentials (username/password)
5. Если используется TLS — убедитесь, что DC поддерживает LDAPS
6. Проверьте firewall на DC

### Объекты не создаются

**Симптом**: Логи показывают "Created", но объектов нет в destination

**Решения:**

1. Проверьте: не включен ли **Dry Run Mode**?
2. Проверьте логи на наличие CONFLICT — возможно, объекты уже существуют
3. Проверьте права администратора в destination DC

### Много DEFERRED ссылок

**Симптом**: В Preview большое количество "Deferred references"

**Пояснение**: Это нормально, если группы ссылаются на пользователей из других OU, которые еще не мигрированы.

**Решение:**

1. Мигрируйте остальные OU
2. Запустите повторную миграцию первого DN — DEFERRED ссылки разрешатся автоматически

### CONFLICT при повторном запуске

**Симптом**: Логи показывают "CONFLICT - exists but not tracked"

**Пояснение**: Объект существует в destination, но не записан в базу данных миграции (возможно, создан вручную).

**Решение:**

Приложение НЕ перезаписывает такие объекты из соображений безопасности. Варианты:

1. Удалить объект в destination вручную, затем запустить миграцию снова
2. Оставить как есть — объект будет пропущен

### База данных миграции

Расположение:

```
~/.config/DirectoryObjectsMigrator/migration.db
```

Если база данных повреждена:

```bash
rm ~/.config/DirectoryObjectsMigrator/migration.db
```

Приложение создаст новую при следующем запуске. **Внимание**: История миграций будет потеряна.

### Логи

Логи сохраняются в:

```
~/.config/DirectoryObjectsMigrator/logs/
```

Имя файла:
```
migration_<YYYYMMDD_HHMMSS>.log
```

При проблемах — откройте лог-файл и найдите строки с `[ERROR]` или `[CRITICAL]`.
